# DocuRAG

A document knowledge base API built with FastAPI.

## Project Overview

DocuRAG is a backend learning project designed to support document ingestion,
text processing, vector retrieval, and source-grounded question answering.

The project is being developed incrementally, with a focus on API design,
automated testing, configuration management, and reproducible development
environments.

## Current Features

- FastAPI application initialization
- Health check endpoint (`GET /health`)
- Automatically generated Swagger UI documentation (`/docs`)
- Environment-based configuration using Pydantic Settings
- PostgreSQL-backed document metadata CRUD
- Database migrations using Alembic
- PDF and TXT upload endpoint with content validation
- PDF text extraction with page mapping
- Text chunking with source character offsets
- Evidence validation for chunk text and PDF page ranges
- Original PDF storage and download for uploaded PDF documents
- Automated tests using pytest

## Planned Features

The following features are not yet implemented:

- Text embeddings and vector similarity search
- pgvector integration
- Redis caching
- Source-grounded question answering
- Docker Compose deployment
- Retrieval evaluation with different chunk sizes and Top-K settings

## Local Setup

Clone the repository or navigate to the project directory.

Create a virtual environment:

```bash
python3.11 -m venv .venv
source .venv/bin/activate
```

Install dependencies:

```bash
python -m pip install -r requirements.txt
```

Create the local configuration file:

```bash
cp .env.example .env
```

Start the API:

```bash
python -m uvicorn app.main:app --reload
```

## Document API

The current document API supports PostgreSQL-backed CRUD operations for document metadata.

### Create a Document

**Request**

```http
POST /documents
Content-Type: application/json
```

```json
{
  "title": "FastAPI Guide",
  "filename": "fastapi.pdf"
}
```

**Example Response — 201 Created**

```json
{
  "id": 1,
  "title": "FastAPI Guide",
  "filename": "fastapi.pdf",
  "created_at": "2026-10-08T08:00:00Z"
}
```

The timestamp above is illustrative. Actual timestamps are generated by the server.

### Available Operations

| Method | Endpoint | Description |
|---|---|---|
| POST | `/documents` | Create document metadata |
| GET | `/documents` | List documents |
| GET | `/documents/{document_id}` | Retrieve a document |
| DELETE | `/documents/{document_id}` | Delete a document |

### Error Handling

- `422`: Invalid request data or unsupported fields
- `404`: Document does not exist
- `204`: Document deleted successfully

### Current Limitations

- Scanned PDFs require OCR, which is not currently supported.
- Upload parsing stores extracted text, but embedding and vector retrieval are not implemented yet.
- Chunk generation exists in the service layer and tests, but there is no
  public API endpoint for triggering rechunking yet.

## Upload API

The upload API accepts PDF and TXT files through multipart form data.

```http
POST /documents/upload
Content-Type: multipart/form-data
```

Successful uploads create a document record, store extracted text, and return file metadata.

For uploaded PDFs, the original PDF can be downloaded inline:

```http
GET /papers/{document_id}/file
```

### Database Architecture Notes

**ORM Model vs. API Schema**

SQLAlchemy ORM models define how data is mapped to PostgreSQL tables, including
primary keys, foreign keys, constraints, and relationships. Pydantic schemas
define how API requests are validated and how responses are serialized.

**Transaction Management**

A transaction is committed after a successful database write operation. If an
operation fails before commit, the Session rolls back to prevent an incomplete
transaction from affecting subsequent operations. Database-generated fields can
be loaded using `refresh()`.

**Data Persistence**

Document records are stored in PostgreSQL rather than process memory. Records
remain available after the FastAPI application restarts.

**Testing**

Database integration tests use a separate PostgreSQL test database and
SQLAlchemy SAVEPOINT-based transaction isolation. Tests cover document CRUD,
request validation, missing resources, and cascading deletes.

### Running tests

Run the test suite using the isolated database bootstrap:

python -m scripts.run_tests -q --tb=short

The bootstrap validates that the target database is docurag_test
before importing pytest or application modules.

Do not run database integration tests against docurag_dev.



## Multi-Step Research Agent (Day 12)

DocuRAG includes a bounded, LangGraph-based research workflow for comparing evidence across multiple academic papers.

The workflow supports document-aware retrieval, structured fact extraction, source quotation verification, evidence coverage assessment, and one supplementary retrieval round. It uses PostgreSQL-backed tools and can run with a DeepSeek LLM adapter.

**Current limitations:** Exact quotation verification does not guarantee semantic correctness. The generated reports distinguish verified source quotations from unreviewed model claims, and task-specific research conclusions may require additional human validation.

### Evaluation

Five real cross-paper research questions were executed using two PostgreSQL-stored documents.

| Metric | Result |
|---|---:|
| Research questions executed | 5 |
| Tool calls | 21 |
| Verified quotations | 46 |
| Rejected quotations | 8 |
| Exact quotation match rate | 85.2% |
| LLM tokens | 57,074 |

These metrics reflect execution and source matching, not end-to-end answer accuracy.

### Run

```bash
python -m scripts.run_tests -q --tb=short
python -m scripts.evaluate_day12_real --question 1
```

Real evaluation requires a configured PostgreSQL database, the evaluation documents, and a DeepSeek API key. Document IDs are currently specific to the local evaluation database.

For implementation details, measured results, and known limitations, see [Day 12 Evaluation Report](docs/day12_report.md).
